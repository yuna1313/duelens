# 사용자 세션·학기 API 구현

2026-11-25. `feature/user-session`에서 구현했습니다. Spring Security 7.2.0·Spring Session JDBC 4.2.0을 사용합니다.

## 완료 범위

- [x] GET `/api/health`: DB 연결 상태만 공통 응답으로 제공, 내부 관리 경로 접근 차단
- [x] GET `/api/v1/session`: 서버 쿠키·CSRF 토큰·시작 전 사용자 UUID 준비
- [x] POST `/api/v1/workspace/start`: guest 사용자 최초 저장, 학기 생략 허용·중복 시작 방지
- [x] GET/PATCH `/api/v1/workspace`: 세션 사용자만 조회·선택 학기 저장, 버전 충돌 검사
- [x] GET `/api/v1/terms`: 본인의 과목·선택 학기에 등장하는 학기만 반환
- [x] Spring Session 공식 테이블·속성을 Flyway V3로 생성하고 JDBC로 보관
- [x] 실제 서버 재시작 후 같은 세션의 사용자 복원·본인 학기 저장 확인

입력의 임의 사용자 ID를 소유권 근거로 사용하지 않습니다. API 본문·쿼리의 알 수 없는 항목을 거부하고, `X-User-ID` 같은 헤더로 세션 사용자를 바꿀 수 없습니다. 과목·과제 API는 아직 구현 전이며 각 자원의 조회·변경·재연결 소유권 검사는 해당 API 단계에서 추가합니다.

## 호출 순서

1. GET `/api/v1/session` → 쿠키와 `data.csrfToken`을 받습니다. 첫 응답은 `state=new`, `userId=null`입니다.
2. POST `/api/v1/workspace/start` → `{}` 또는 확인한 `initialTerm`을 보냅니다. 첫 성공 시 세션 ID와 CSRF 토큰을 갱신합니다.
3. GET `/api/v1/session` → 새 CSRF 토큰을 받은 뒤 다음 쓰기 요청에 전달합니다.
4. PATCH `/api/v1/workspace` → 선택 학기·`expectedRevision`을 전달합니다. 같은 값은 버전을 올리지 않으며 오래된 버전은 거부합니다.

클라이언트는 쿠키를 직접 읽거나 저장하지 않고, CSRF 토큰은 메모리에서 관리합니다. 프론트엔드 API 연결은 후속 작업입니다.

## 보안·운영 설정

- 쿠키: `DUELENS_SESSION`, HttpOnly, SameSite=Lax, 호스트 전용, Path=/api. Secure는 기본 true이며 로컬 HTTP 설정·테스트에서만 false로 지정합니다.
- 쓰기: CSRF 검증을 유지하며 Origin을 검사합니다. 로컬 Vite 출처 두 개와 실제 같은 서버 출처만 허용합니다. 운영 출처는 `DUELENS_WRITE_ORIGINS`로 정확한 목록을 지정합니다. 전역 CORS 허용·비밀번호 로그인·기본 사용자 계정은 제공하지 않습니다.
- 입력: JSON 최대 256 KiB, 중복 키·알 수 없는 필드/쿼리·숫자/문자열 자동 형변환·잘못된 학기·버전을 거부합니다.
- 응답: 처리한 성공·실패 모두 HTTP 200, `success`, `code`, `message`, `data`. 실패 상세는 message에 보내며 내부 예외·토큰·비밀번호를 응답에 포함하지 않습니다. 개인 응답에는 no-store를 적용합니다.
- 세션 신규 발급: 프로세스 기준 주소별 분당 60개, 주소 버킷 최대 4096개로 제한하며 초과 시 RATE_LIMITED와 Retry-After를 반환합니다. 프록시 헤더를 임의의 실제 사용자 주소로 신뢰하지 않습니다. 다중 서버의 공통 제한 정책은 배포 단계에서 정합니다.
- 현재 개발 세션의 비활성 만료는 30분입니다. 만료·쿠키 삭제 후 기존 사용자에 자동 연결하지 않습니다. 게스트 보관·복구·정식 계정 전환 정책은 공개 서비스 전에 확정합니다.

## 소스 배치와 커밋

`common/`은 공통 응답·오류·상태 경로, `security/`는 세션·CSRF·쿠키·요청 제한, `workspace/`는 사용자 저장·선택 학기·현재 API를 담당합니다. API와 저장 로직을 분리하고 JDBC 쿼리는 값 바인딩을 사용합니다.

공통 응답, 세션·보안 기반, 사용자 저장·학기 처리, HTTP API를 별도 커밋으로 나눴으며 필요한 검증은 구현과 함께 묶었습니다.
